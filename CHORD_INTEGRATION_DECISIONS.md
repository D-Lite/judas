# Chord integration decisions (22 October 2026)

This is a documentation and local-code audit, **not** a live Chord tenant test. No Chord API key, workspace ID, teammate ID, configured WhatsApp connector, or incoming media sample is present in this checkout or its process environment. We must not label a merchant as connected merely because they entered a phone number or generated an AlertCheck MCP key.

## Product boundaries

1. **Postgres is the source of truth for attempts.** Chord turns, customer messages and merchant notifications are projections of a verified attempt. Receipt text, OCR, or a numerical reference pattern cannot by themselves create a confirmed payment. The mock provider must remain plainly marked as synthetic.
2. **One merchant is one security principal.** For a production Chord deployment, prefer a dedicated workspace and teammate/MCP registration per merchant, with that merchant's bearer key. Chord's MCP guide says an empty `mcp_server_ids` assignment exposes *all enabled workspace servers* to a teammate. Before enabling another merchant server, assign explicit nonempty server lists to all relevant teammates. Our MCP server derives merchant identity from the bearer key rather than a model-supplied argument. Test cross-shop access through a real Chord tool call.
3. **Use the existing native WhatsApp channel first, if it is actually configured and supports inbound image/PDF media and outbound replies in this tenant.** Chord's concepts and thread docs describe WhatsApp as a channel and show `media` on turns, but the public guides do not establish this tenant's connector configuration, media download permissions or report attachment delivery. Probe with an invented PDF/image and inspect the resulting thread/turn before committing to this path. If the native channel cannot deliver the required media/tool context, use our own WhatsApp provider bridge plus Chord's signed external-chat callback; that is a separate, material integration, not a switch we can flip in the portal.
4. **The portal is the guaranteed merchant feed.** Every persisted status change appears there. The merchant's separate WhatsApp assistant chat is an outbound projection only after a channel route has been proved. Do not use Chord event subscriptions for the feed: they run a one-off agent task and create no conversation/thread. Do not use the inline chat endpoint as a delivery mechanism for asynchronous operator replies: it has no return path. Do not use `POST /v1/threads/{id}/messages` for automated payment notices unless Chord confirms that representing these as *human-operator* turns is acceptable; that endpoint expressly authors messages as a human operator.
5. **A pending result is a state, not a second payment.** Store one attempt keyed by `(merchant_id, reference)` and one event per transition. Recheck provider state through an explicit poll or provider webhook; on pending→confirmed/failed, preserve the original attempt and correlate the new notification to the earlier reference/attempt ID. Chord's public guides do not promise WhatsApp message-edit support; where editing/reactions are absent, send a linked follow-up instead of claiming the original message was tagged.
6. **Alert calculation is deterministic.** For each receiving account, over a rolling 60 minutes and >20 distinct attempts, alert at >=50% pending+failed. Recommend the configured backup only when its own recent sample proves healthy. Alert suppression/cooldown should prevent repeat unsolicited messages; a merchant can still ask the assistant for current health.

## Chord facts that affect implementation

- [MCP connections](https://api.chordhq.xyz/docs/mcp-servers/): public HTTPS Streamable HTTP endpoint; register with bearer auth, discover exact tool names, check health status (HTTP 200 may still mean `error`), assign the server to the teammate, and run an actual tool-using conversation. Registration and health do not prove business-tool execution. Chord Connect delegated tokens cannot manage these `/v1` MCP routes.
- [External chat](https://api.chordhq.xyz/docs/external-chat/): one bridge per workspace. Inbound messages are HMAC-signed over `timestamp + "." + raw_body_bytes`; 200 means queued, not answered. Stable `sender_id` makes the thread, `session_id` routes replies back, and `message_id` deduplicates a redelivery for 24 hours. Agent and human replies both reach the callback. The inbound JSON body is limited to 256 KiB and documented as text, not a general PDF upload path. Verify callback signature and route by `conversation_id`.
- [Threads](https://api.chordhq.xyz/docs/threads/): turns carry `media` descriptors, but actual media access needs a tenant/channel test. `POST /v1/threads` proactive creation is external-chat only. `POST /v1/threads/{id}/messages` writes a human-operator turn, not a neutral system event. Thread reads can support a merchant inbox only with correctly scoped `thread:read` permission and workspace isolation.
- [Event subscriptions](https://api.chordhq.xyz/docs/event-subscriptions/): one event yields one agent run and a webhook result; it does not append a conversation. Use only for genuinely background agent jobs, never to fake the merchant chat feed.
- [Scheduled tasks](https://api.chordhq.xyz/docs/scheduling/): WhatsApp delivery exists via the workspace connector, but scheduled tasks are not a generic immediate status-notification API. They are also held back during human takeover/pause and subject to admission/billing checks. Do not make per-payment delivery depend on this untested path.
- [Artifacts](https://api.chordhq.xyz/docs/artifacts/): a workspace file store using presign/upload/confirm; upload does not itself deliver a PDF into WhatsApp. Reports may be stored here after generation, but delivery must be verified separately.

## Live acceptance gates before calling this a working WhatsApp agent

1. With account-owner authorization, get a scoped Chord API key and actual workspace/teammate IDs. Read teammate channel status; verify the WhatsApp connector is **connected**, not merely listed.
2. Connect one invented merchant to a dedicated development workspace. Register this shop's HTTPS MCP endpoint disabled, set explicit teammate server scope and tool allowlist, enable, discover tools, inspect health, and observe a real `verify_payment` call in a test thread.
3. Send invented Nigerian receipt image and PDF files over the configured WhatsApp test number. Inspect thread turns and tool context for media descriptors or retrievable file bytes. Test both text-native and scanned PDF extraction; document failures.
4. Verify confirmed, failed, pending, unknown-reference, amount mismatch, account mismatch, duplicate, cross-merchant, and pending-resolution paths. Confirm the customer sees only provider-backed status, and the portal stores exactly one attempt.
5. Prove a merchant WhatsApp route and one outcome delivery with a channel message ID/receipt, then test a linked pending follow-up and a report. If the connector cannot do this, retain the portal feed and explicitly mark WhatsApp merchant delivery unavailable; do not silently imply it succeeded.
6. Test callback/webhook signatures, retries, idempotency, outages and human takeover before live customers. Real payment-feed access requires a separately authorized bank/PSP integration; the synthetic provider must never be treated as settlement evidence.

## Current result

The repository currently passes local tests for portal tenant isolation, connection-key rotation, verification and account health. It has no live Chord registration, WhatsApp media ingestion, Chord callback, outbound merchant-chat sender or PDF delivery. Those are acceptance gates, not finished features.
